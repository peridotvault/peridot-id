# ANT-868 B4: V5 cluster/chain domain binding — decision record

## Decision

**V5 = new discriminants + new domain separators (additive-only).**
In-place rebinding of V3/V4 payloads was rejected: it would invalidate every
in-flight signature at upgrade time (owner intents, session grants with up to
30d `validUntil`) with no settlement path. Additive V5 keeps V3/V4 verifiers
byte-frozen; old signatures settle through their natural TTL sunset while new
clients opt into V5 per instruction.

- Gas optimization: V5 adds two 32-byte parts (program id + cluster id) to
  the hashed payload only — no new accounts, no new syscalls, no storage
  writes on the verify path. Cost delta vs V3 is one extra sha256 block
  compress (~ns-scale, unmetered on-chain beyond the fixed precompile cost).
- Reentrancy & checks-effects-interactions: V5 siblings preserve their V3
  counterparts' ordering exactly (nonce burn before CPI/value movement;
  pinned by `ant16_ordering_tests` + `include_str!` source pins).
- Access control: unchanged — same authority checks, same PDA derivation.
- Oracle & randomness risk: n/a (no feeds; the cluster id is build-baked,
  not oracle-read).
- Upgradeability safety: N/A to the SVM program (no proxy); EVM side needs
  no change (see §5). New SVM state: none (CLUSTER_ID is a baked const, not
  account state) — existing vaults use V5 immediately, no migration.
- Reorg & finality handling: cluster binding is orthogonal to reorgs; TTL +
  nonce semantics unchanged.
- Key management: no keys committed; probe uses ephemeral generated keys.
- Fuzz & invariant testing: payload-vector unit tests pin SDK↔program byte
  parity (see §6); validator probe covers the cross-cluster property.

## Problem (B4)

SVM owner payloads bind `op-tag ‖ account_id ‖ nonce ‖ … ‖ expiry` under
`DOMAIN_V3`/`DOMAIN_V4` — but **no cluster binding**. The same vault PDA
exists on every cluster by design (same seeds + same program id), and the
program cannot observe its own cluster (no cluster sysvar). A leaked/stolen
assertion is therefore valid on *every* cluster until its nonce is consumed
or its ≤600s TTL expires. PoC-D (`docs/security/ant860-poc/poc-d-replay.mjs`)
proved it: one V3 withdraw assertion settled on two isolated validators.

EVM never had this hole: every EVM payload binds `block.chainid`
(`test_AdvCrossChainReplayFails` pins it).

## V5 design

New domains: `PID|SOLANA|SMART_ACCOUNT|v5`, `PID|SOLANA|SESSION|v2`
(reserved). New discriminants: 20-21 implemented (UpdateAuthorityV5,
ExecuteV5 — the authority-hijack and value-movement threats), 22-29 (owner)
and 30-32 (session) RESERVED.

V5 payload = `sha256(DOMAIN_V5 ‖ op-tag ‖ program_id ‖ cluster_id ‖ <V3 tail>)`.
Instruction layouts are byte-identical to their V3 counterparts — the version
lives in the discriminant + domain, never in extra fields, so SDK serializers
are shared and review diff is minimal.

Bound sources (both spoof-proof, both recomputed on-chain — never from
instruction bytes a relayer could substitute):

- `program_id`: the entrypoint argument. Kills cross-*program* replay (same
  PDA seeds under a different program id).
- `CLUSTER_ID`: build-baked const from `PID_CLUSTER_ID` (base58, 32 bytes —
  deploy with the cluster's `solana genesis-hash`). Kills cross-*cluster*
  replay. Unset ⇒ all-zero local default (build warning); named-cluster
  deploys (`PID_PROGRAM_ID_REQUIRED=1` / `SOLANA_CLUSTER=testnet*|mainnet*`)
  fail closed at build time — a shared id across clusters would silently
  preserve the hole V5 exists to close.

Why baked-const and not vault-stored: vault data length is fixed at creation,
so existing vaults cannot grow a cluster field; a baked const works for old
and new vaults alike with zero state migration. The residual is deployment
discipline (distinct ids per cluster), enforced by the build gate + the
replay probe below.

## Migration path + sunset + TTL reasoning

1. Land V5 alongside V3/V4 (this task: proving slice 20-21; child issue for
   22-32 following the same mechanical pattern).
2. SDK/wallet cut over to V5 builders per path; relayers accept both
   discriminants during transition.
3. Old-domain sunset is natural, no flag day:
   - Owner paths: every V3/V4 assertion carries ≤600s TTL (`MAX_TTL_SECS`,
     `check_expiry`). 600s after clients stop minting V3/V4, no V3/V4
     assertion can verify — the old domain is dead by construction.
   - Session/permission paths (≤30d `validUntil` / `MAX_PERMISSION_TTL`):
     the V5 session discriminants (30-32) ship with the child issue; until
     then, pre-existing grants age out naturally (≤30d) and rotation
     revokes them early via the B3 epoch.
4. No instruction is ever *removed*: frozen entrypoints stay for archaeology
   and old-SDK decoders (repo convention since V4).

## Nonce + rotation story (per-cluster, not global)

Nonces are per-vault state, and vault state is per-cluster — so nonces are
inherently per-cluster. V5 keeps per-vault nonces; there is deliberately **no**
global/cross-cluster nonce service (that would be cross-chain infrastructure
for a problem the cluster binding already kills).

Consequences, stated explicitly:

- A V5 assertion for cluster A fails on cluster B at the *challenge* check
  (`InvalidChallenge`), before nonce/expiry logic — nonces never come into
  play cross-cluster.
- Rotation (`updateAuthority[V5]`) revokes sessions **on the cluster where it
  executes** (B3 epoch is vault state). Operators must rotate per cluster;
  a rotation on A does not revoke B's sessions — consistent, because session
  PDAs themselves live on exactly one cluster.
- Within one cluster, the existing guarantees hold: nonce burn before
  effects (replay ⇒ spent-nonce failure), ≤600s TTL (stolen assertion dies
  fast), rotation ⇒ epoch bump ⇒ all live sessions stale.

## EVM side

No change required: EVM payloads already bind `block.chainid + address(this)`
on every path (owner execute/rotate/activate, permission grant/revoke/exec,
1271, permissionId). The B4 work is SVM-only; EVM coverage is the pre-existing
`test_AdvCrossChainReplayFails` forge test.

## Residual risks

1. Same-binary-same-`CLUSTER_ID` deployed on two clusters (operator error):
   V5 replay works between them until TTL/nonce. Mitigated by the named-
   cluster build gate; cannot be closed in-code (the program cannot observe
   its cluster).
2. V3/V4 paths remain replayable cross-cluster during the sunset window
   (≤600s per assertion by TTL). Accepted: killing them early would brick
   in-flight signatures — the very breakage additive-only avoids.
3. V5 session discriminants (30-32) not yet implemented: session lifecycle
   assertions (register/revoke/close) stay TTL-bound until the child issue
   lands. `session_execute` itself needs no domain (Ed25519 session-signer +
   per-cluster seq + 30min inactivity window, unchanged).
4. B3 interplay: `update_authority_v5` must gain the epoch bump when ANT-863
   B3 lands on `paperclip` (one line + test; flagged in the child issue).
   Until then, a V5 rotation moves authority without revoking sessions —
   operators needing revocation today use V3 rotation (B3 branch) or explicit
   per-session revoke.

  V5-vs-V3 separation, discriminant pins, source-binding pins, ordering pin).
- `forge test`: 100 passed (95 baseline + 5 B3).
- Validator cross-cluster replay probe: `contracts/svm/smart-account/tests/probe-v5-replay.mjs`
  (two isolated validators, distinct baked `CLUSTER_ID`s). Evidence 2026-10-30
  (program `2GYE…PS2Nx`, clusters `H4Hq…P1D`/`f164…599`):
  `PART1-A: V3 withdraw nonce0 settled on A` /
  `PART1-B: V3 withdraw nonce0 settled on B (same assertion — B4 baseline)` /
  `PART2-A: V5 rotate nonce1 settled on A` /
  `PART2-B: V5 rotate (A-bound) REJECTED on B as required` /
  `PART2-C: V5 rotate (B-bound) nonce1 settled on B — control passes`.
  The B-side rejection is challenge-scoped by construction (same PDA, same
  nonce 1, same expiry, same program id — the only divergent input is the
  bound cluster id) and the B-bound control proves the validator accepts
  well-formed V5.
