# Peridot ID — V3 Architecture Audit

Status: completed — generated by task `docs/tasks/001-architecture-audit-report.md` (2026-08-10).
Source of truth: `docs/prds/PRD_v3.md`. Every claim below cites repository evidence.

## 1. Current Architecture

**Monorepo (pnpm workspaces).** `apps/api` (NestJS 11 + Prisma 6 + PostgreSQL),
`apps/docs` (Fumadocs + Next.js), `packages/openapi` (API source of truth),
`packages/types` (shared DTOs), `packages/sdk-js` (browser fetch client).
See `README.md`, `pnpm-workspace.yaml`.

**API runtime.** NestJS REST API, cookie-based JWT authentication. No GraphQL. The OpenAPI
document `packages/openapi/src/openapi.yaml` is the API source of truth and is served by the
API itself at `GET /v1/openapi.yaml` (`apps/api/src/openapi/openapi.controller.ts`). Swagger UI
is exposed at `/docs` (`apps/api/src/main.ts`). Global `ValidationPipe({ whitelist: true })`
(`apps/api/src/main.ts`) and rate limiting via `@nestjs/throttler`
(`apps/api/src/app.module.ts:13`, per-route `@Throttle` in `auth.controller.ts`).

**Modules.** `auth`, `identity`, `profile`, `openapi` (`apps/api/src/app.module.ts:15-18`).

**Deployment.** Vercel serverless (`apps/api/vercel.json`, framework `nestjs`); PostgreSQL on
Supabase — refresh-token state lives in the `sessions` table, Postgres is the only datastore
(`docs/ARCHITECTURE.md`; commit `0c11a47` dropped Redis).

**Authentication flow** (documented in `apps/docs/content/docs/(general)/authentication.mdx`):
`POST /v1/auth/login` returns the Google authorization URL → `GET /v1/auth/google` redirects to
Google consent → `GET /v1/auth/google/callback` exchanges the code, resolves or creates the
identity, and sets two HttpOnly cookies (`peridot_access`, `peridot_refresh`) →
redirect to `CLIENT_SUCCESS_URL`.

**SDK.** `@peridot/sdk-js` is a thin `fetch` client, one class per domain
(`PeridotAuth`, `PeridotIdentity`, `PeridotProfile`), cookie handling via
`credentials: "include"`, 401 handling that never recurses on `/v1/auth/*`
(`packages/sdk-js/src/index.ts`).

## 2. Existing Identity Model

- **PID.** `identities.id` is a `pid_<ULID>` string, generated by `newPid()`
  (`apps/api/src/common/pid.ts`). Immutable by construction — no code path rewrites it.
  Status enum `active | suspended | deleted` with soft-delete field `deletedAt`
  (`apps/api/prisma/schema.prisma:11-29`). **No PID deletion endpoint exists.**
- **Credentials.** One row per login method in `identity_credentials`. `(provider,
  providerUserId)` is unique — the source of truth (`schema.prisma:56`). `email` is nullable
  metadata **only**, deliberately not an identity key (`docs/DATABASE.md` invariants;
  `apps/docs/content/docs/(general)/authentication.mdx`: "The **email is metadata only**"). The
  Google login path (`upsertGoogleIdentity`, `apps/api/src/auth/auth.service.ts:38-73`) never
  checks email: an unknown `(provider, providerUserId)` always creates a new identity.
- **Profile.** 1:1 with identity; `username` unique, `^[a-z0-9_]{3,20}$`
  (`apps/api/src/common/username.ts:3`), `usernameChangedAt` set on change
  (`apps/api/src/profile/profile.service.ts`).
- **Unlink guard.** Removing a credential is rejected when it is the last one
  (`apps/api/src/identity/identity.service.ts:31-32`). Unlink deletes only the credential row —
  never the identity.
- **Sessions.** Rotating refresh tokens: `jti` stored in `sessions`, each rotation revokes the
  previous token, and a reused (already-rotated) token is rejected
  (`apps/api/src/auth/auth.service.ts:113-133`; covered by `auth.service.spec.ts`). One
  `devices` row per client; sessions hang off devices (`schema.prisma:60-82`). Access tokens
  carry `sub` (PID) and are validated against identity status per request
  (`apps/api/src/auth/jwt.strategy.ts`).
- **Naming convention.** API error messages are in Indonesian (e.g.
  `identity.service.ts:29,32`, `profile.service.ts:29`).

## 3. Existing Wallet Capability

**None exists.**

Evidence (audited 2026-08-10):

- No `wallet` model or relation in `apps/api/prisma/schema.prisma`.
- Zero matches for `solana|@solana|ethers|viem|web3` in `pnpm-lock.yaml`.
- No wallet/blockchain references in `apps/api/package.json`, `apps/api/src/**`, or
  `packages/openapi/src/openapi.yaml`.
- No wallet endpoint in `docs/API_SPEC.md` or `apps/docs` docs.
- V1 PRD lists **Wallet** and **Blockchain** as explicit non-goals (`docs/prds/PRD.md`,
  "Non-goals"). No roadmap entry mentions a chain (`docs/ROADMAP.md`).

There is no blockchain dependency, no key-management code, and no architectural evidence
restricting any particular chain or custody model.

## 5. Architecture Proposal

Smallest coherent architecture consistent with the repository, presented per PRD §14. Items
marked **deferred** are open until tasks 002/003 decide them; they are listed, not invented.

- **Wallet ownership:** a `wallets` table on `identities` (PID → wallet), matching the PRD's
  `PID ├── Credentials └── Wallets` shape. No provider (Google) fields on the wallet record
  (PRD §5, §11). **Deferred to 003:** exact fields, cardinality, delete behavior, key-material
  storage.
- **API:** REST under `/v1/wallet`, following the `identity/` module pattern (controller +
  service + Prisma, `JwtAuthGuard` + `@CurrentUser()`), OpenAPI-first via
  `packages/openapi/src/openapi.yaml`. **Deferred to 003:** endpoint set depends on creation
  timing (in-flow vs explicit action).
- **Auth boundary:** reuse the existing cookie-JWT/session mechanism; wallet routes require
  `JwtAuthGuard`; ownership resolved strictly from the token. No new transport or auth model.
- **Contract:** extend `@peridot/types` and `@peridot/sdk-js` with a `PeridotWallet` domain
  class. No new dependencies.
- **Custody/key model, chain, AA:** **deferred to 003** — the repository gives no evidence;
  PRD §7 requires documenting the decision rather than guessing.
- **Migration:** additive schema only; **no backfill of wallets for existing users** unless
  003 decides otherwise (PRD §12: no silent wallet creation).

## 6. Risks

- **Security — custody:** once wallet key material exists, database compromise and
  account-takeover blast radius depend entirely on the custody decision (003). The current
  model has no key material beyond env-based JWT secrets; that must not silently change.
- **Security — authz:** a miswired wallet route could expose another PID's wallet; strict
  token-derived ownership is required (task 006/008).
- **Authentication — email collision:** the PRD §4 vs repo conflict means current logins may
  create a second PID for an email tied to another account (no merge, no check). Task 002 must
  resolve before 004 changes login behavior.
- **Migration / data integrity:** production data may already contain duplicate non-null
  credential emails; enforcing uniqueness later (002 option A) needs a pre-migration audit.
  Wallet schema must be additive; existing V2 rows must survive `db:deploy`.
- **Wallet custody / operational:** Vercel serverless + Supabase gives no persistent server
  process or HSM — server-side signing or key storage has operational constraints that must be
  analyzed in 003 before any implementation.
- **Destructive lifecycle:** wallet deletion and PID-deletion semantics are undefined today;
  blockchain-backed wallets may have on-chain consequences that a DB delete cannot undo
  (003, 009).

cookie-JWT auth boundary; PID immutability and provider uniqueness are existing invariants.

(PRD §7):

  Account Abstraction relevance, creation timing, lifecycle/deletion/PID-deletion semantics,
